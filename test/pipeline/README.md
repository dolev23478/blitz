# בדיקת התהליך המלא (pipeline)

הבדיקה מכניסה קלטים בפורמט של אוסף טלגרם ושל אוסף X, ומעבירה אותם דרך הקוד האמיתי:
- **החיבור של גל:** `TelegramListenerService` ו־`XScraperCronService`.
- **הסינון וזיהוי השפה של לאוניד.**
- **הטרנספורמר של יואב:** מיפוי וולידציה.

בסוף היא בודקת שההודעה שהייתה נשלחת לקפקא נראית כמו שצריך.

רק השליחה לקפקא מוחלפת ברכיב שרושם את ההודעה (`RecordingPublisher`). הרכיב הזה משתמש באותה סריאליזציה של יואב, ולכן המפתח והערך שנרשמים זהים למה שקפקא היה מקבל. Redis כבוי. לא נשלח כלום לרשת.

## הרצה

```bash
npm run test:pipeline
```

## הוספת מקרה

ב־[`cases.ts`](cases.ts) מעתיקים מקרה קיים ומשנים את הטקסט ואת `expect`:

```ts
{
  id: 'tg-he-pigua',
  title: 'Hebrew with "פיגוע" is sent with he and the term',
  message: tg(1001, 'דיווח ראשוני: בוצע פיגוע דקירה בצומת, יש פצועים'),
  expect: { sent: true, languages: ['he'], matches: ['פיגוע'] },
}
```

- **`sent: false`:** הפוסט צריך להיפסל, וב־`why` כותבים למה.
- **`languages` ו־`matches`:** ערכים שחייבים להופיע בהודעה.
- **`notMatches`:** מילים שאסור שיופיעו. למשל, מילה שמגיעה מפוסט אחר באותו באץ'.
- **`mediaType`:** הערך המדויק של `media_type`, למקרים שבודקים מדיה.

## מה עוד נבדק

- **התאמה לחוזה:** כל הודעה עוברת ולידציה מול RAW_REPORT כפי שהוא מוגדר ב־schemas.html (20.10.2026), ב־[`raw-report.contract.ts`](raw-report.contract.ts). כשנקבל מ־DE את קובץ ה־JSON Schema, מחליפים את הקובץ הזה בקובץ שלהם.
- **מפתח קפקא:** המפתח שווה ל־`report_id` כמחרוזת, והמזהה יציב לאותו פוסט.
- **הודעה שנכשלת:** לא עוצרת את שאר ההודעות באותו אירוע.
- **פוסט כפול:** נשלח פעם אחת בלבד. הרכיב שרושם את ההודעות מחליף את השולח, ולכן אם מניעת הכפילויות תמומש בתוך השולח, צריך לעדכן את הבדיקה הזאת.
